# ModulPOS

E-commerce integration platform: imports supplier XML feeds, prices products with templates, validates them and sends them to
marketplaces (Trendyol first; Hepsiburada / Pazarama / Çiçeksepeti partly).

```
server/   Express + Prisma (PostgreSQL) API, cron jobs          → Render web service (Singapore)
client/   React + Vite single page app                          → Render static site
content/  AI Content Intelligence admin panel (Vite + React)    → its own Render static site (content.modulpos.com); backend in server/src/content
docs/     Trendyol API notes
render.yaml  Render Blueprint      DEPLOY_RENDER.md  deployment & operations
```

## Commands
```bash
cd server && npm install && npm test            # unit tests (no database needed)
cd server && npx prisma generate && npm run dev # needs DATABASE_URL / DIRECT_URL / JWT_SECRET in server/.env
cd client && npm install && npm run dev         # VITE_API_BASE_URL in client/.env
cd client && npm run test:smoke                 # renders the products screen in jsdom with a mocked API
```

## Architecture notes (non-obvious)
* **One pricing engine** (`server/src/services/pricingEngine.js`) prices products for the list, the send routes and the cron.
  Sale VAT comes from the product (chosen when the XML source is added), never from the pricing template.
  The template screen (`client/src/pages/pricing/`) is ONE screen with two template types: **Tek kâr** (one profit,
  percent of purchase or fixed TL) and **Kademeli kâr** (`profitTiers`, any number of rows by purchase price; `MAX_TIERS` = 1000 is only a safety ceiling). Costs are single values
  (shipping, other, commission, service fee). Keep it that way: no marketplace names/tariffs in this screen.
  Tax options (added 2026-11-12 on the owner's request, they are a VAT payer): **KDV mükellefiyim** (`inputVat`, purchase VAT `purchaseVatRate` default 20) and **stopaj** (`withholdingPct`, 1% of the
  VAT-exclusive price). With them, profit = price - commission - service fee - other - shipping - purchase - stopaj - VAT payable, where VAT payable = VAT of the sale minus the VAT inside purchase,
  shipping, commission, service fee and other costs (20%, `EXPENSE_VAT`). `profitBreakdown()` is the ONE place that turns a price into a profit and `priceWith()` its exact inverse; both go through
  `taxModel()`. Without the options (every template saved before them) the earlier formulas run untouched, so changing a template's options changes its prices: it is the owner's decision per template.
  The engine can still evaluate older stored rules that use `shippingTiers` (+`shippingTiersExVat`) or `margin_on_gross`,
  but no screen creates them; editing such a rule warns and drops them on save.
  A sale price typed in by hand for one product on one marketplace lives in `ProductPriceOverride` and is applied INSIDE
  `PricingContext` (`priceFor` / `explainFor`), so the list, readiness, sends and the automatic updates all use the same
  number. Never compute or store a sale price anywhere else. If the table cannot be read, pricing falls back to templates.
  **Products added by hand** (no XML source and no feed price: `isHandAdded()` = `xmlSourceId === null && !(xmlPrice > 0)`, strictly null so a caller that did not load the column is never taken for one; a product whose XML source was deleted keeps its feed price and stays an
  ordinary purchase-price product): their `price` is the NET amount the owner wants to keep per sale (the form says so: "Elime kalacak net tutar"), NOT a purchase price. The marketplace price is the same solver asked backwards (`netExplain`, used by
  `PricingContext._resolve` / `priceFor` and `summarizeCoverage`): the template that matches supplies shipping, commission (ONE rate, no per-category rates: the owner chose that), service fee, stopaj and the tax options; its profit settings are ignored. The template's
  `netMode` is the owner's setting for what "100 TL" means: `cash` (default; exactly that stays after commission, shipping, fee, stopaj and the VAT to pay; no purchase) or `purchase` (the amount is a purchase price, profit 0, so the VAT inside it is deducted: cheaper). **`profit`** (added 2026-11-24 because the owner wanted to enter a purchase price and let the template add profit): the template is read like an XML product's, `price` is the PURCHASE price and the template's own profit (percent / fixed / tiers) is applied; `pricesAsNet(product, conditions)` in `pricingEngine.js` is the single place that decides "net amount or purchase price" (`isHandAdded && netMode !== 'profit'`), used by `_resolve`, `priceFor` and `summarizeCoverage`; `/pricing/calculate` and the route validation (`cash | purchase | profit`) follow it. Changing the template's mode reinterprets every hand product's number (alış <-> net): the workspace says so before the owner does it.
  Owner's real values, amount 100: cash 302.84 TL, purchase 276.87 TL. Scope: `xmlSourceIds: ['none']` ("Elle eklenen ürünler" in the template screen, which then replaces the profit inputs by the net choice); an unscoped template also prices hand-added products (as net, cash by default); a
  template of one XML source never does. No amount (0 TL) = no price. A hand-typed sale price still wins; the profit shown at it is what stays. To be sendable such a product also needs barcode, brand and picture URLs (the form requires them) and a Trendyol category from the product-level tab.
  **Pictures of hand-added products** (`ProductImageUpload`, `services/hostedImages.js`, public `GET /api/uploads/<id>.<jpg|png|webp>` in `routes/uploads.js`, upload `POST /products/images`, helper `client/src/pages/products/imageTools.js`): the form accepts picture addresses AND photos from the device
  (shrunk in the browser to 2000 px JPEG; the server accepts only JPG/PNG/WebP by their first bytes, 3.5 MB each, 40 unused and 120 MB per store). The free hosting has no disk, so the bytes live in the database and are served WITHOUT login (random id) because the marketplace has to download them. They are only a
  loan: `releaseSent` (after every Trendyol status sync AND a 15-minute cron, `releaseAll`) asks Trendyol (`getProducts` approved and not yet approved) for each sent product that still carries uploads, and only when it shows ITS OWN addresses for all pictures (none of ours, at least min(own, 8)) the product's `images`
  are replaced by Trendyol's addresses and our copies are deleted; otherwise nothing is deleted and it is tried again. Never delete earlier: a picture Trendyol has not downloaded yet must stay reachable. Uploads no saved product used are removed after a day (`purgeOrphans`); a product's save attaches the uploads in its list and deletes those it dropped
  (`attach`); deleting the product cascades. NOT verified against a real Trendyol account: the answer shape (`images[].url`) comes from Trendyol's documented product query, the release logic is unit-tested with a fake service. The brand field of a NEW hand-added product is filled from the Trendyol store settings (`client/src/pages/products/storeBrand.js`, connection `config.defaultBrandName`): with `brandStrategy: 'override'` ("Kendi markam") it is read-only because the send uses the store brand for every product anyway (`resolveProductBrandId`), with the XML strategy it is the editable fallback. **Required attributes in the form** (`client/src/pages/products/RequiredAttributes.jsx`, `services/attributeForm.js`, `POST .../product-categories/attribute-form`): once a Trendyol category is chosen, its REQUIRED attributes load inside the form with their allowed values and a first answer where one is known (order: a Trendyol page's hint, the title/description via the same careful reader as the bulk step, then the connection's default answers; each answer says where it came from; nothing is invented).
  On save the order is product -> category assignment (which runs the automatic fill) -> `PUT .../product-categories/product-attributes`: the owner's choices go on top as the product's OWN values (`from: 'form'`, never shared with the category, never replaced by the default answers); values are validated against the allowed list (free text only where `allowCustom`). Lists are cut at 600 values.
  **Link import** (`TrendyolImport.jsx`, `services/trendyolPage.js`, `POST /products/trendyol-import`): the form can be filled from a Trendyol product link and stays editable (price is shown only as information, the store brand is kept, the category is the page's own id when it is in our tree with the same name, otherwise a flagged GUESS by name). **Trendyol blocks servers** (Cloudflare 403, checked 2026-11-21 from this machine with several user agents and from an independent fetcher), so the server's own read of a link usually answers `422 blocked: true` and the form asks for the PAGE SOURCE (Ctrl+U, copy all, paste), which is parsed the same way.   **XML -> hand-added products** (2026-11-24, button "XML’den ürün ekle" on the products page, `XmlHandImportModal.jsx` + `xmlFile.js`, `services/xmlHandImport.js`, routes `POST /products/xml-import/read` and `POST /products/xml-import`, live e2e `xml-hand-import`): the owner has the goods but no photos, so a file (read in the browser, decoded by the encoding the file declares, sent as `text/xml`, 30 MB) or an address gives ONLY name, description, picture addresses (`//` -> `https:`, max 12), barcode / stock code and the category text; the XML's price, brand, stock and VAT are NEVER used (brand = the store's, from `storeBrandOf`; VAT, stock and "use the barcode" are the person's choices in the dialog). Rows are created exactly like `POST /products` creates them (no XML source, no feed price = `isHandAdded`, price 0), so XML sync never touches them and the owner updates them by hand. Two steps: `read` parses with `streamProductObjects` (`responseStream` for a file, SSRF-safe address otherwise), maps with `suggestMapping` + the person's field choices (the parser UPPER-CASES tag names, so paths look like `URUNADI`) and keeps the cleaned rows in a short-lived memory cache under a token (45 min, one reading per user, three in all, ~30 MB: the free host has 512 MB; a restart = 410 "yeniden okuyun"); `create` takes token + row numbers (batches of 200) and skips what the store has (same SKU / barcode) and what `maxProducts` does not allow. A SKU is the XML's stock code, else the barcode, else `XML-<sha1 of the name>` (stable, so the same file twice finds the same products). Pictures stay the supplier's addresses (not copied into our storage: the 120 MB hosted-image cap is for the owner's own photos). Products without a picture are listed but not ticked by default (Trendyol refuses them). **One rule for the stock codes and one for the barcodes** (dialog card "Stok kodu ve barkod kuralı", `readCodeRules` / `codesFor`, `POST /products/xml-import/preview { token, codes }`): sku = keep | affix | replace | barcode | counter (prefix + start + row number + suffix), barcode = keep | none | sku | affix | replace | generate (own EAN-13: digits prefix + running number + check digit; a made-up barcode matches no Trendyol catalogue product, the dialog says so). A running number is `start + row number`, so the same file gives the same codes; the rule is validated on the server (never trusted from the page) and the preview, the table and the write all use `codesFor`; the "already there" check runs on the NEW codes (`existing` / `preview`), two rows ending with one code are told apart (`file`). The older `useBarcode: false` option still means barcode rule `none`.
